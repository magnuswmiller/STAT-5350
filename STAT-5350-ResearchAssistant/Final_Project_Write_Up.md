## Problem Statement
Having previously worked as a researcher in a lab at CU Boulder in addition to starting work on my master's thesis, I have found the process of research to be quite fun but also quite time consuming. When I am running behind, it is more likely that I am stuck trying to track down a piece of data or a specific method in a pool of articles. Additionally, when I am writing up my work, I often leave the bibliography to the end as it is my least favorite task. Through speaking with my classmates and colleagues, I have found I'm not alone in this sentiment.

This application aims to alleviate some of these common frustrations amongst students and researchers. I specifically wanted a tool that could help me and others quickly and accurately parse large research articles to find specific information in context, summarize swaths of text into concise descriptions, and most importantly, automatically create formatted bibliographies.

## Design Considerations
As mentioned above, the main goal of this application is to make research more efficient by streamlining the research process. I chose to focus on three key features: parsing articles for specific information in context, summarizing texts into concise descriptions, and automatically create formatted and downloadable PDF bibliographies.

Before I could tackle any of these features, I first had to deal with loading the documents to prime the LLM and be able to leverage *RAG* frameworks. I wanted to be able to drag-and-drop or select files from my file explorer on my device rather than have to load them via the command line. As a result, I decided on using a graphical user interface rather thana command line design. This allowed me to ingest and embed multiple large files at a single time. In addition to the drag-and-drop functionality, using a GUI makes for a more intuitive and user-friendly experience overall which helps when sharing this tool with others.

With the overall implementation design, I was then able to focus on the more specific functionality mentioned before. For the underlying models, I made a deliberate choice to default to locally hosted open source models via *Ollama* rather than relying on paid API services. This decision was driven by a few factors. First, running models locally means that uploaded documents never leave the user's machine, which is an important consideration when working with unpublished research or sensitive materials. Second, it removes any dependency on API keys or usage costs, making the tool accessible to anyone regardless of their budget. That being said, I recognized that local models have their limitations in terms of speed and accuracy, so I built in optional support for *OpenAI* models that can be enabled with a single change in the configuration file. This gives users the flexibility to trade off between privacy and performance depending on their needs.
 
For the Q&A functionality, I chose to leverage a RAG pipeline rather than relying on the LLM alone. The core problem with asking an LLM to answer questions about a document without RAG is that the model has no knowledge of the document's contents and would have to rely on its training data, which would lead to inaccurate or fabricated responses. By first retrieving the most relevant chunks of text from the uploaded documents and passing those directly to the model as context, the LLM is grounded in the actual content of the documents. This same principle applies to summarization and citation extraction, where the model is given only the relevant portion of a document to work with rather than being asked to generate content from scratch. The result is a tool that is far less prone to hallucination and much more useful in practice.

## Performance Evaluation
Overall, the *Research Assistant App* performs quite well. The tests I performed included multiple mathematical finance journal articles, resumes, and other local PDF files I had on my computer. These files ranged in length from a single page to roughly 45 pages. The app was able to ingest and embed multiple files in under 30 seconds (this process takes some time as I chose to embed the source text on ingestion rather than on summarization or Q&A to make the experience more streamlined). Due to the preemptive embedding process, the app is able to handle most Q&A queries in under 20 seconds and summaries in under a minute. It is important to note that these metrics are dependent on the length of the files as well as the complexity of the questions or queries asked. Finally, citation extraction and bibliography construction took less than 10 seconds for each file. In each of the above cases, the responses were quite accurate. The most common errors were in regard to extracting citation information. The app excelled at pulling authors and titles, but did struggle to establish a publishing date on multiple accounts. This might be attributable to the fact that I was using pre-print articles that don't explicitly list a publishing date.

It is important to note that all testing was conducted locally on a single machine using *nomic-embed-text* as the embedding model and *llama3:b* as the LLM model. While these pre-trained models are great for smaller local tasks, they may not be suitable for larger or more complex files thus making the response times listed above quite *loose*. I was unable to test the *OpenAI* functionality due to a lack of API keys. That being said, I would expect responses using those available models and APIs to be far faster and more accurate.

## Limitations and Known Issues
While the app performs well within its intended scope, there are a few notable limitations worth addressing. The first and most significant is the in-memory vector database. Because all embeddings are stored in memory at runtime, the vector database is wiped every time the app is restarted. This means users have to re-ingest their documents each session, which can be time consuming for larger collections of files. This was an intentional design choice to keep the prototype simple and free of external dependencies, but it is the most obvious area for improvement in a future version.
 
A second limitation is that the app relies on *pypdf* for text extraction, which works well for standard digital PDFs but cannot handle scanned documents. If a user uploads a scanned PDF where the content exists as an image rather than selectable text, the app will ingest the file without error but the extracted text will be empty, resulting in zero chunks in the vector database and no useful responses. Adding OCR support would address this but was outside the scope of this prototype.
 
Finally, the reliability of citation extraction is tied directly to the quality of the underlying model. When using smaller local models like *llama3:8b*, the model occasionally fails to return well-formed JSON for citation metadata, which causes the extraction to fall back to a placeholder entry in the bibliography. This is handled gracefully in the app but is worth noting as a known limitation of using smaller open source models for structured output tasks.

## Ethical Considerations
There are a few ethical considerations worth discussing in the context of this tool. The first is the risk of hallucination. Despite the use of a RAG pipeline to ground the model's responses in the actual content of uploaded documents, language models can still generate plausible-sounding but inaccurate responses, particularly when the answer to a question is not clearly present in the retrieved context. Users should treat the app's responses as a starting point for research rather than a definitive source of truth, and should always verify important information against the original documents.
 
The second consideration is data privacy. When using the default Ollama configuration, all processing happens locally on the user's machine and no data is sent to any external service. This makes the tool well-suited for working with sensitive or unpublished materials. However, when the OpenAI option is enabled, document text is sent to OpenAI's API for processing. Users should be aware of this distinction and make an informed choice about which configuration is appropriate for their use case.
 
Finally, there is the question of academic integrity in the context of citation generation. The bibliography feature is designed to assist with formatting rather than to replace the user's responsibility to accurately attribute sources. Citation metadata extracted by the model should always be reviewed and verified before being used in an academic submission, as errors in author names, dates, or titles are possible especially with pre-print or informally formatted documents.

## Conclusion and Future Improvements
The *Research Assistant App* successfully demonstrates the integration of multiple deep learning techniques into a practical and usable tool. The combination of RAG, embeddings, semantic search, and LLM-powered generation produces a prototype that genuinely addresses the research workflow pain points described in the problem statement. The addition of a clean GUI and Docker deployment makes the tool accessible and easy to share.
 
Looking ahead, there are several improvements that would meaningfully extend the app's capabilities. The most impactful would be replacing the in-memory vector database with another solution that would allow embeddings to be stored between sessions and eliminate the need to re-ingest documents on every restart. Adding OCR support via a library like *pytesseract* would extend compatibility to scanned PDFs. On the model side, testing with larger or more capable models (including the OpenAI integration) would likely improve the reliability of citation extraction and the overall quality of responses. Finally, adding multi-turn conversation memory to the Q&A tab would make the interface feel more natural and allow users to ask follow-up questions in context.
